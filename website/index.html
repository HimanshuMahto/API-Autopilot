In plain words

Your app has a shop front that people see and a back office that does the real work. API Autopilot tests the back office.

Same API. Only one of them asked the second question.

What is an API?

The part of your product that other software talks to. Every login, order and payment passes through it, whether it comes from your website, your mobile app or a partner.

What goes wrong?

Most tests check that things work when used properly. The expensive bugs show up when someone does the unexpected, like asking for an order that is not theirs.

What does Autopilot do?

It plays the unexpected customer. It runs dozens of careful experiments, writes down exactly what broke, and shows the steps to see it for yourself.

How it works

Four steps. No test scripts to write.

  1. 01

    Finds your API

    Point it at your project, your running app or a spec file. It finds the description of your API and learns every action it offers and the rules it promises to follow.

    $ autopilot init --project .
  2. 02

    Tries what nobody tested

    The AI plans experiments. What if a quantity is negative? What if one customer asks for another's order? Each runs as a real request against your test environment.

    Plan: … (7 hypotheses)
  3. 03

    Follows the trail

    When an answer looks odd, it digs further, the way a curious tester would, instead of moving on to the next item on a list.

    Follow-up: … Round 2: running 6 scenario(s)
  4. 04

    Proves it, then saves it

    Each suspected bug is repeated from a clean start. Only the ones that repeat every time are reported, and each is saved as a test for after the fix.

    confirmed Server error in cancelOrder (2/2)

Setup

Point it at your API however you have it. It finds the rest.

Your project folder

Finds a spec file in the repo, or builds one from the code for FastAPI and Django REST. For Spring Boot, NestJS, ASP.NET, Express and Flask, it tells you how to let it start the app.

$ autopilot init --project ~/code/my-api

Your running app

Tries the addresses frameworks publish their spec on, such as /openapi.json, /v3/api-docs and /swagger.json, and uses the first that answers.

$ autopilot init --url http://localhost:8000

A spec file

OpenAPI 3 or Swagger 2.0, JSON or YAML, from a file or a link. A copy is saved so every run tests the same version.

$ autopilot init --spec openapi.yaml

Starts your app for each run

Give it the start command once. It waits until the app answers, tests it, and stops it afterwards. If the app is already running, it uses that.

Logs in on its own

It spots your login endpoint in the spec and signs in two test users at the start of every run, so there are no tokens to copy or refresh.

What it finds

The problems that reach the news. Checked on every single answer your API gives.

  • Customers seeing each other's data

    Bob opens an order that belongs to Alice, and the API hands it over.

    alicePOST /orders201 Created
    bobGET /orders/{id}200 OKshould be 404
    builtin.auth_differential

  • Doors left unlocked

    Something that should need a login answers anyone who asks.

    GET /orders no token → 200 OK expected 401 builtin.auth_required

  • Rules that are not enforced

    The manual says a quantity must be between 1 and 100. The API accepts minus five.

    POST /orders {"quantity": -5} → 201 Created spec.constraint

  • Crashes

    Cancelling the same order twice ends in a server error instead of a polite refusal.

    POST /orders/{id}/cancel twice → 500 expected 409 builtin.server_error

  • Answers that break the contract

    A price promised as a number arrives as text, which can break the apps that read it.

    "price": "19.99" spec says number builtin.schema_conformance

  • Surprises the manual never mentioned

    The API replies in a way its own documentation does not list.

    GET /me → 302 not listed in spec builtin.undocumented_status

  • Internals leaked in errors

    An error message shows the database query, a stack trace or the server's file paths, which helps attackers map the system.

    POST /api/images → 500 "INSERT INTO rate_limits …" builtin.error_leak

  • 7 checks on every response.

    Each check is plain code, not an AI opinion, so the same response always gets the same verdict. That makes a saved bug safe to use as a test.

Safe by design

The AI suggests. Plain code decides.

AI is good at imagining what might break and bad at being right every time. So Autopilot never lets the AI send a request or declare a bug on its own. Every request passes a safety gate first, and every verdict comes from fixed checks that give the same answer each time.

Looks before it touches

It starts in read-only mode. It will not create, change or delete anything until you switch that on.

Stays where you put it

It only talks to the addresses you list, and it treats anything that looks like your live system as look-only.

Your data stays yours

The AI sees the shape of an answer, never its contents. Passwords and access keys never leave your machine.

Re-checks without AI

Saved bugs run again with no AI at all, so the result is the same every time. Made for automatic checks before a release.

Get started

The code comes with a small online shop that has four bugs planted in it. Run Autopilot against it and watch it find them. Then point it at your own API.

autopilot run --max-requests 50

Questions

Straight answers.

Do I need to be technical to use it?

Today it runs from the command line, so a developer sets it up. The report it produces is written in plain language, with the steps to reproduce every problem, so anyone on the team can read it.

Can I run it on my live product?

Please don't. It sends deliberately wrong input and can create test data. Use a staging or local copy. As a backstop, it switches to look-only mode for any address that looks like a live system.

Does the AI see my customers' data?

No. The AI is given your API's description and the shape of each answer, such as "a list of orders, each with an id and a total". It is never given the contents, and it never sees passwords or access keys. You can also run with no AI, in which case nothing leaves your machine except the test requests to your own API.

What does it cost?

The product itself is free. If you use the AI planner, you pay your AI provider directly. A full run against our demo shop cost about one cent on Groq. Re-checking saved bugs uses no AI and costs nothing.

Will it find every bug?

No tool does. Autopilot checks the rules your API's description states, plus a set of rules every API should follow. A business rule that is written nowhere, like "a total must equal price times quantity", is not checked yet.

What does my API need?

An OpenAPI 3 or Swagger 2.0 description, which most modern frameworks produce for you, and two test accounts so it can check that one customer cannot reach another's data. You don't have to find the description yourself: point Autopilot at your project or your running app and it looks for it.

Which frameworks does it work with?

Any HTTP API with an OpenAPI or Swagger description. It reads FastAPI and Django REST projects directly, and finds the description on a running Spring Boot, NestJS, ASP.NET, Express or Flask app. JSON requests and file uploads are both supported.
